本工具如何估算计算资源与存储资源How compute and storage resources are estimated

← 返回计算器Back to calculator

1. 输入Inputs

工具的输入是未压缩的业务数据量（GB/TB/PB）和基础设施类型。所有路径都从这两个值出发推导节点数与每节点规格。

The inputs are the uncompressed business data size (GB/TB/PB) and the infrastructure type. Every path derives node counts and per-node specs from these two values.

2. 通用规则Common rules

压缩比Compression

列式存储 + 压缩后，落盘数据 ≈ 业务数据 ÷ 压缩比（默认 2，可在高级选项调整）。存算分离（容器）路径按源规范不启用压缩。

With columnar storage + compression, on-disk data ≈ business data ÷ compression ratio (default 2, adjustable in advanced options). The container path applies no compression, per its source spec.

onDiskTB = dataTB ÷ compressionRatio

计算资源约束Compute constraint (8c32G / TB)

基线：每 1 TB 落盘数据配一个 8 vCPU + 32 GB 内存的 segment，可支撑最高约 80 并发——满足大多数数据仓库场景。依据 MPP 7.7 官方内存最佳实践：每 segment 内存最低 8GB、best practice 32GB；单查询内存 statement_mem = gp_vmem_protect_limit × 0.9 ÷ 预期并发数，32G × 0.9 ÷ 80 ≈ 368MB/查询，属健康区间。并发要求更高时，按该公式线性放大每 segment 资源（高级选项）：≤120 并发 ×1.5，≤160 并发 ×2。

Baseline: one 8 vCPU + 32 GB segment per TB of on-disk data supports up to ~80 concurrent queries — enough for most data-warehouse workloads. Grounding, from the MPP 7.7 memory best practices: 8GB minimum and 32GB best-practice per segment; per-query memory statement_mem = gp_vmem_protect_limit × 0.9 ÷ expected_concurrency, and 32G × 0.9 ÷ 80 ≈ 368MB per query is a healthy value. For higher concurrency the per-segment resources scale linearly (advanced options): ≤120 concurrent ×1.5, ≤160 ×2.

perNodeTB    = min( vCPU ÷ (8 × f),  memGB ÷ (32 × f) )     # f = 并发系数：≤80→1（默认）/ ≤120→1.5 / ≤160→2
computeNodes = CEIL( onDiskTB ÷ perNodeTB )
perNodeTB    = min( vCPU ÷ (8 × f),  memGB ÷ (32 × f) )     # f = concurrency factor: ≤80→1 (default) / ≤120→1.5 / ≤160→2
computeNodes = CEIL( onDiskTB ÷ perNodeTB )

最终节点数Final node count

存储与计算两个维度分别算出所需节点数，取较大者，再向上取偶数（MPP 习惯，便于 primary/mirror 对称分布）。结果页的徽标会标明是存储受限还是计算受限。

Storage-driven and compute-driven node counts are derived independently; the larger wins, then rounds up to an even number (MPP convention for symmetric primary/mirror placement). The result badge shows which constraint binds.

nodes = roundUpToEven( max( storageNodes, computeNodes ) )

3. 物理机Physical · Cloudberry MPP

存储侧按金融行业生产集群实践（2023）的方法：数据存两份（primary + mirror），操作系统与文件系统占标称容量约 10%，并保留 20% 空闲空间：

Storage follows a financial-industry production method (2023): data stored twice (primary + mirror), ~10% of nominal capacity consumed by OS and filesystem, and 20% kept free:

needTB       = onDiskTB × 2 ÷ 0.9 ÷ 0.8
storageNodes = CEIL( needTB ÷ arrayTB )      # arrayTB = 单节点 RAID 后可用容量
needTB       = onDiskTB × 2 ÷ 0.9 ÷ 0.8
storageNodes = CEIL( needTB ÷ arrayTB )      # arrayTB = usable RAID capacity per node

NVMe 的 RAID 说明：主流 2U 机型支持 12–24 个 U.2/U.3 直连盘位；NVMe 硬件 RAID5 需三模（tri-mode）RAID 卡（如 Dell PERC H755N/H965i、Broadcom MegaRAID 9560/9600 系）或 Intel VROC。另一常见路线是 NVMe 不做 RAID（JBOD、每盘独立 XFS），冗余完全依赖 primary/mirror——吞吐更高，但单盘故障即触发 mirror 接管，本工具默认按更保守的 RAID5 计算容量。

NVMe RAID note: mainstream 2U servers take 12–24 direct U.2/U.3 bays; hardware NVMe RAID5 needs a tri-mode controller (Dell PERC H755N/H965i, Broadcom MegaRAID 9560/9600) or Intel VROC. JBOD with mirror-only redundancy is a common higher-throughput alternative — a single disk failure then triggers mirror takeover; this tool sizes conservatively with RAID5.

Coordinator 固定 2 台（主+备），同级 CPU/内存，系统盘 RAID1 + 小容量数据阵列。计算约束按整机物理核数（64C）与内存代入通用公式。

Coordinator is fixed at 2 (primary + standby), same CPU/memory class, RAID1 system disks + a small data array. The compute constraint uses the host's 64 physical cores and memory in the common rule.

每主机段布局Segments per host

每台主机部署的 primary 数 = 主机资源 ÷ 单 segment 配额（8c/32G × 并发系数），CPU 与内存取较小者；mirror 与 primary 同数量，用 spread mirroring 打散到其他主机（结果页按 N primary + N mirror 展示，并给出每 primary 实际管理的数据量）。例：物理机 64 核/512G → 8 primary + 8 mirror；虚拟机/云主机 8–24 vCPU → 1–3 primary，与 MPP 官方虚拟化建议（每 VM 1–4 个 segment 实例）一致。

Primaries per host = host resources ÷ per-segment quota (8c/32G × f), the tighter of CPU and memory; mirrors equal primaries, spread across other hosts (the result page shows N primary + N mirror plus the actual data per primary). Example: a 64-core/512G physical host → 8 primary + 8 mirror; VM/cloud nodes at 8–24 vCPU → 1–3 primaries, matching the official 1–4 segments-per-VM guidance.

MPP 7.7 文档指出每主机 segment 数需综合：核数、内存、网卡数、存储容量、primary/mirror 混布、主机上的 ETL 及其他进程。相关内存参数按官方公式配置：

The MPP 7.7 docs list the factors for segments per host: cores, RAM, NICs, attached storage, the primary/mirror mixture, and ETL or other processes on the host. Memory parameters follow the official formulas:

gp_vmem（≥256G 主机）      = ((SWAP + RAM) − (7.5GB + 0.05 × RAM)) ÷ 1.17
gp_vmem_protect_limit      = gp_vmem ÷ max_acting_primary_segments
statement_mem              = gp_vmem_protect_limit × 0.9 ÷ 预期并发数
gp_vmem (host ≥256G)       = ((SWAP + RAM) − (7.5GB + 0.05 × RAM)) ÷ 1.17
gp_vmem_protect_limit      = gp_vmem ÷ max_acting_primary_segments
statement_mem              = gp_vmem_protect_limit × 0.9 ÷ expected_concurrency

4. 虚拟机VM · Cloudberry MPP

单节点可用容量在数据盘标称容量上打三重折扣：70% 水位、÷2 镜像、再留 1/3 工作空间：

Per-node usable capacity applies three discounts to nominal disk capacity: 70% watermark, ÷2 mirror, plus 1/3 workspace:

usableTB     = storageTB × 0.7 ÷ (2 + 1/3)      ≈ storageTB × 0.3
storageNodes = evenUp( TRUNC( onDiskTB ÷ usableTB ) + 2 )   # +2 为保底余量
usableTB     = storageTB × 0.7 ÷ (2 + 1/3)      ≈ storageTB × 0.3
storageNodes = evenUp( TRUNC( onDiskTB ÷ usableTB ) + 2 )   # +2 headroom

5. 云主机Cloud · Cloudberry MPP

节点数公式与虚拟机相同，单节点存储取所选云方案的数据盘容量。每个云厂商提供两套方案：

Same node-count formula as VM, with per-node storage from the selected cloud scheme. Two schemes per provider:

  • 云盘方案（来源：MPP 7.7 官方 Cloud Technical Recommendations）：AWS r5.4xlarge + 3×EBS ST1/GP3；Azure Standard_E16s_v5 + 3×P40 Premium SSD；GCP n2-highmem-8 + pd-ssd。数据可靠性依赖云盘，支持快照。
  • 本地盘方案（生产部署实践）：AWS i3en.2xlarge、Azure Standard_L8s_v3、GCP c3d-standard-8-lssd 本地 NVMe。吞吐更高、成本更低，可靠性依赖 primary/mirror 双副本。
  • Managed-disk schemes (MPP 7.7 official Cloud Technical Recommendations): AWS r5.4xlarge + 3×EBS ST1/GP3; Azure Standard_E16s_v5 + 3×P40 Premium SSD; GCP n2-highmem-8 + pd-ssd. Durability from cloud disks, snapshot-capable.
  • Local-NVMe schemes (production practice): AWS i3en.2xlarge, Azure Standard_L8s_v3, GCP c3d-standard-8-lssd. Higher throughput, lower cost; durability relies on primary/mirror.

附加建议：Azure 使用 UDP interconnect 并预留端口 65330；GCP 官方建议用更多的小节点（相对 AWS）。

Extra guidance: on Azure use the UDP interconnect and reserve port 65330; on GCP prefer more, smaller nodes (vs AWS).

6. 容器 / K8s · 存算分离Container / K8s · Compute-storage separation

存算分离形态下数据本体在对象存储（OSS，按需扩容），计算节点本地盘只是缓存/工作区，因此逻辑相反：并发档位决定单 Segment 规格与其管理的数据量：

With compute-storage separation the data lives in object storage (OSS, scaled on demand) and local disks are cache/workspace only, so the logic inverts: the concurrency tier sets the per-segment spec and the data each segment manages:

7. 汇总与可承载容量Totals & usable capacity

资源汇总 = Σ(各角色节点数 × 每节点规格)。「可承载数据量」是把最终节点数代回存储公式反推的上限——它 ≥ 你输入的数据量，差值就是本方案的自然余量。

Totals sum count × per-node spec across roles. "Usable data capacity" inverts the storage formula at the final node count — it is ≥ your input, and the difference is the recommendation's natural headroom.

capacityTB(物理机) = nodes × arrayTB × 0.9 × 0.8 ÷ 2 × compressionRatio
capacityTB(VM/云)  = nodes × usableTB × compressionRatio
capacityTB(physical) = nodes × arrayTB × 0.9 × 0.8 ÷ 2 × compressionRatio
capacityTB(VM/cloud) = nodes × usableTB × compressionRatio
