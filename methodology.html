计算方法说明 Methodology

本工具如何估算计算资源与存储资源 · How compute and storage are estimated

← 返回计算器 / Back

1. 输入 · Inputs

工具的输入是未压缩的业务数据量（GB/TB/PB）和基础设施类型。所有路径都从这两个值出发推导节点数与每节点规格。

Input is the uncompressed business data size plus the infrastructure type. Everything else is derived.

2. 通用规则 · Common rules

压缩比 Compression

列式存储 + 压缩后，落盘数据 ≈ 业务数据 ÷ 压缩比（默认 2，可在高级选项调整）。存算分离（容器）路径按源规范不启用压缩。

onDiskTB = dataTB ÷ compressionRatio

计算资源约束 Compute constraint（8c32G / TB）

基线：每 1 TB 落盘数据配一个 8 vCPU + 32 GB 内存的 segment，可支撑最高约 80 并发——满足大多数数据仓库场景。依据 MPP 7.7 官方内存最佳实践：每 segment 内存最低 8GB、best practice 32GB；单查询内存 statement_mem = gp_vmem_protect_limit × 0.9 ÷ 预期并发数，32G × 0.9 ÷ 80 ≈ 368MB/查询，属健康区间。并发要求更高时，按该公式线性放大每 segment 资源（高级选项）：≤120 并发 ×1.5，≤160 并发 ×2。

perNodeTB    = min( vCPU ÷ (8 × f),  memGB ÷ (32 × f) )     # f = 并发系数：≤80→1（默认）/ ≤120→1.5 / ≤160→2
computeNodes = CEIL( onDiskTB ÷ perNodeTB )

Baseline: one 8 vCPU + 32 GB segment per TB of on-disk data supports up to ~80 concurrent queries (per the best-practice statement_mem formula: 32G × 0.9 ÷ 80 ≈ 368MB per query; docs recommend 8GB minimum, 32GB best-practice per segment). Higher concurrency scales per-segment resources linearly.

最终节点数 Final node count

存储与计算两个维度分别算出所需节点数，取较大者，再向上取偶数（MPP 习惯，便于 primary/mirror 对称分布）。结果页的徽标会标明是存储受限还是计算受限。

nodes = roundUpToEven( max( storageNodes, computeNodes ) )

3. 物理机 · Physical (Cloudberry MPP)

存储侧按金融行业生产集群实践（2023）的方法：数据存两份（primary + mirror），操作系统与文件系统占标称容量约 10%，并保留 20% 空闲空间：

needTB       = onDiskTB × 2 ÷ 0.9 ÷ 0.8
storageNodes = CEIL( needTB ÷ arrayTB )      # arrayTB = 单节点 RAID 后可用容量

三档硬件预设（arrayTB 取 RAID5 后可用盘数 × 单盘容量）：

预设CPU / 内存数据盘RAID单节点可用网卡
基础款 · SAS2×32C / 512G24 × 1.2TB 10K SAS每 12 盘一组 RAID5 ×2（22 盘可用）26.4 TB2×10GbE
高吞吐款 · SSD2×32C / 1024G24 × 960GB SSD同上21.1 TB2×10GbE/25GbE
现代款 · NVMe2×32C / 1024G DDR512 × 3.84TB NVMe U.2RAID5（11 盘可用）42.2 TB2×25GbE

Coordinator 固定 2 台（主+备），同级 CPU/内存，系统盘 RAID1 + 小容量数据阵列。计算约束按整机物理核数（64C）与内存代入通用公式。

Storage: data ×2 (mirror), ÷0.9 OS/FS overhead, ÷0.8 to keep 20% free, divided by the per-node usable RAID capacity. Compute uses the common rule with 64 physical cores per node. Coordinator ×2 fixed.

每主机段布局 Segments per host

每台主机部署的 primary 数 = 主机资源 ÷ 单 segment 配额（8c/32G × 并发系数），CPU 与内存取较小者；mirror 与 primary 同数量，用 spread mirroring 打散到其他主机（结果页按 N primary + N mirror 展示，并给出每 primary 实际管理的数据量）。例：物理机 64 核/512G → 8 primary + 8 mirror；虚拟机/云主机 8–24 vCPU → 1–3 primary，与 MPP 官方虚拟化建议（每 VM 1–4 个 segment 实例）一致。

MPP 7.7 文档指出每主机 segment 数需综合：核数、内存、网卡数、存储容量、primary/mirror 混布、主机上的 ETL 及其他进程。相关内存参数按官方公式配置：

gp_vmem（≥256G 主机）      = ((SWAP + RAM) − (7.5GB + 0.05 × RAM)) ÷ 1.17
gp_vmem_protect_limit      = gp_vmem ÷ max_acting_primary_segments
statement_mem              = gp_vmem_protect_limit × 0.9 ÷ 预期并发数

Primaries per host = host resources ÷ per-segment quota (8c/32G × f), the tighter of CPU and memory; mirrors equal primaries, spread across other hosts. Physical 64c/512G → 8P+8M; VM/cloud 8–24 vCPU → 1–3 primaries, matching the official 1–4 segments-per-VM guidance. Memory parameters follow the official gp_vmem / gp_vmem_protect_limit / statement_mem formulas above.

4. 虚拟机 · VM (Cloudberry MPP)

单节点可用容量在数据盘标称容量上打三重折扣：70% 水位、÷2 镜像、再留 1/3 工作空间：

usableTB     = storageTB × 0.7 ÷ (2 + 1/3)      ≈ storageTB × 0.3
storageNodes = evenUp( TRUNC( onDiskTB ÷ usableTB ) + 2 )   # +2 为保底余量

三档虚拟机规格，按数据量自动推荐（可手动覆盖）：

规格适用vCPU / 内存 / 数据盘盘吞吐宿主机要求
Lite≤5 TB8 / 64G / 2T SSD≥500 MB/s可共享宿主机
Medium≤50 TB16 / 128G / 4T SSD≥1000 MB/sCPU 超配 ≤1:2
Large>50 TB24 / 256G / 8T SSD≥1500 MB/s独占宿主机，1:1 物理资源

Per-node usable ≈ 30% of nominal disk (0.7 watermark, ÷2 mirror, +1/3 workspace). Profile auto-selected by data size; override in advanced options.

5. 云主机 · Cloud (Cloudberry MPP)

节点数公式与虚拟机相同，单节点存储取所选云方案的数据盘容量。每个云厂商提供两套方案：

  • 云盘方案（来源：MPP 7.7 官方 Cloud Technical Recommendations）：AWS r5.4xlarge + 3×EBS ST1/GP3；Azure Standard_E16s_v5 + 3×P40 Premium SSD；GCP n2-highmem-8 + pd-ssd。数据可靠性依赖云盘，支持快照。
  • 本地盘方案（生产部署实践）：AWS i3en.2xlarge、Azure Standard_L8s_v3、GCP c3d-standard-8-lssd 本地 NVMe。吞吐更高、成本更低，可靠性依赖 primary/mirror 双副本。

附加建议：Azure 使用 UDP interconnect 并预留端口 65330；GCP 官方建议用更多的小节点（相对 AWS）。

Same formula as VM with per-scheme disk capacity. Managed-disk schemes follow the MPP 7.7 official recommendations; local-NVMe schemes follow production deployment practice.

6. 容器 / K8s · Compute-storage separation

存算分离形态下数据本体在对象存储（OSS，按需扩容），计算节点本地盘只是缓存/工作区，因此逻辑相反：并发档位决定单 Segment 规格与其管理的数据量：

segments = max( 2, CEIL( dataTB ÷ TB_per_segment ) )

固定平台组件：Meta 服务 6 实例（UnionStore ×4 + Metadata-Proxy + Storage-Broker）、WebConsole ×11 小容器、负载均衡、OSS。

Data lives in OSS; the concurrency tier sets per-segment size and TB-per-segment. Fixed platform components (meta services, console, LB) are added on top.

7. 汇总与可承载容量 · Totals

资源汇总 = Σ(各角色节点数 × 每节点规格)。「可承载数据量」是把最终节点数代回存储公式反推的上限——它 ≥ 你输入的数据量，差值就是本方案的自然余量。

capacityTB(物理机) = nodes × arrayTB × 0.9 × 0.8 ÷ 2 × compressionRatio
capacityTB(VM/云)  = nodes × usableTB × compressionRatio

Totals sum count × per-node spec across roles. "Usable data capacity" inverts the storage formula at the final node count — the headroom of the recommendation.
